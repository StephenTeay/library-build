# ROLE

coding agent. Your job has TWO STAGES:

  e-learning portal and digital library for the **Federal School of Statistics,

The audience is a developer who will deploy and maintain the result. Optimize for
correctness, clear contracts, and decisions that are easy to defend.

# 2. INFRASTRUCTURE (perpetual free tiers only)

| Layer | Choice | Constraint |
|---|---|---|
| Frontend | Cloudflare Pages, Vite + React + `vite-plugin-pwa` | Installable PWA, cache-first for UI shell, syllabi, text content |
| Same-origin proxy | Cloudflare Pages Functions | Proxies `/api/*` to the backend so auth cookies are first-party |
| Backend | Node.js (Express or NestJS) on Render free web service | < 512 MB RAM, stateless |
| Database | Neon serverless Postgres (free) | < 500 MB, pooled connection string |
| File storage | Cloudflare R2, **private bucket** | 10 GB free, presigned URLs only |
| Email | Brevo free tier, single-sender verification | No custom domain available |
| Monitoring / keep-alive | UptimeRobot or cron-job.org | `GET /api/health` every 10 min, 07:00-22:00 WAT |

Rules:
- **No custom domain.** Everything lives on free provider subdomains
  (`*.pages.dev`, `*.onrender.com`). Design around this.
- Do not use Supabase (inactivity pausing) or Resend (needs a verified domain for
  arbitrary recipients). Explain each exclusion in one sentence.
- No service with an expiring trial or auto-deleting database.
- Address cold starts honestly: Render spin-down outside ping hours and Neon
  compute wake-up. Specify frontend behavior (skeleton UI, retry with backoff,
  "server waking up" message) rather than pretending pings eliminate it.

# 5. AUTHENTICATION & ONBOARDING

**Sessions:** HTTP-only, Secure, SameSite=Lax cookies, made possible by the Pages
Functions proxy. Choose server-side sessions or short-lived JWT plus rotating
refresh token and justify it in 3 lines. Include CSRF protection, login rate
limiting, and lockout.

**Path A: Bulk CSV import (Registrar/HOD)**
- Schema: `matric_no,email,full_name,department,programme,level,entry_session`
  (`programme` is `ND` or `HND`)
- Stream-parse in batches of 100; never buffer the whole file. Multipart upload
  streamed through the backend. State a max file size.
- Email: lowercase + trim, unique. Matric: trim + uppercase.
- Initial password = sanitized matric number, hashed with Argon2id (state cost
  parameters that fit 512 MB; bcrypt fallback only if justified). Never store plaintext.
- Set `must_change_password = true`, `status = ACTIVE`. Block all non-password-change
  routes until changed.
- **Duplicates:** skip and report (default). Never overwrite existing accounts.
- Produce a downloadable per-row error report. Persist an `import_jobs` record.
- No per-student emails by default (Brevo quota); make it a flag.
- **Security note (required):** default-password-equals-matric is guessable by
  classmates. Mitigate with rate limiting, lockout, forced change on first login,
  and a recommendation for alternatives.

**Path B: Self-registration + approval queue**
- Registration creates `status = PENDING`. Pending users cannot access content.
- Require email verification before the account enters the approval queue.
- Compare the normalized matric number against `admissions_master_list`. A match
  sets `matched_verified = true` (a separate boolean, **not** a status value).
- Admin queue: filter by department/level; HODs and coordinators see only their
  scope; batch-approve verified rows in one action; every action writes to `audit_logs`.
- Send an approval email via Brevo.
- If the matric already exists from CSV import, return a clear "account already
  exists, use login/reset" response.

**Password reset:** hashed, single-use, expiring tokens in a dedicated table.

# 6. CONTENT, STORAGE & EXTERNAL RESOURCES

**Uploads (R2 private):**
- Browser/admin uploads via presigned PUT directly to R2.
- **Confirm step:** client calls `POST /api/resources/confirm` after upload; backend
  verifies the object exists (HEAD), then records the resource. No DB row without a
  verified object.
- Enforce a file-type allowlist and size limits at presign time; set content-type
  and max length on the presigned request.
- Downloads: authorized request -> short-lived presigned GET URL.
- **Offline caching of private files:** the service worker must not cache by
  presigned URL (it expires). Cache keyed by stable resource ID after an
  authenticated fetch, with user-initiated "Save for offline," a storage quota
  indicator, and cache clearing on logout.

**YouTube:** store only `video_id` and `start_seconds`. Render via a lite facade
(thumbnail + click-to-load); never an iframe on page load.

**Library:** `LibraryCatalogProvider` per section 3. Show availability, call number,
and shelf location inside the course module tab.

**Open resource aggregator:** curated link collections (OpenStax, MIT OCW, NBS
portal, DOAB) stored in the DB, plus live search for arXiv and GitHub via public
APIs with server-side caching. Do not assume NBS has a stable API; curate links.

**Data-Saver Mode:** client toggle persisted locally. Suppresses images, embeds,
and notebook previews, shows text-only views, defers non-essential fetches. Audio
summaries are **optional**: define the `audio_url` field and playback UI, but do not
build generation. Lecturers may upload audio files.

**Discussions (Business Admin first, usable anywhere):** threaded posts per course,
moderation by lecturers/HODs, soft delete.

## 9.4 Milestones (in order; each ends with a gate)
Build milestones in order and stop according to RUN SETTINGS. In `checkpoint` mode,
milestones after CHECKPOINT_AFTER are listed in `docs/BUILD_PLAN.md` as

1. **Scaffold:** monorepo, tooling, lint/format, Docker Compose, `.env.example`,
   CI workflow (GitHub Actions free tier: lint + test + build). Gate: `docker
   compose up` brings up the DB, and CI config validates.
2. **Database:** migrations and seed (sample departments, sample courses clearly
   labelled as fake, a bootstrap Registrar script). Gate: migrate up and down
   cleanly on a fresh DB; seed runs.
3. **Auth and permissions:** sessions/cookies, CSRF, rate limiting, lockout,

   every cell of the permission matrix and the lockout/rate-limit paths.
4. **Onboarding:** CSV streaming importer (with error report and `import_jobs`),

5. **Content and storage:** courses, enrollments, resources, R2 presign (PUT, GET,
   confirm), file-type/size enforcement, library provider + admin catalog CSV,

6. **Frontend:** app shell, auth screens, forced password change, student dashboard,
   course module tabs, Lite YouTube component, Data-Saver toggle, offline "Save for

   integration tests pass; production build succeeds; PWA manifest and service

7. **Hardening and docs:** security review pass (authz on every route, input
   validation, headers, secrets scan), bundle-size check on the main route,
   `docs/DEPLOY.md` (verified against current free-tier docs, dated),
   `docs/OPERATIONS.md` (backups, monitoring, NDPA), `README.md`, and a "Known
   limitations & upgrade path" section.

## 9.5 Definition of done (per milestone)
- Code compiles; lint passes; tests for that milestone exist and **pass when
  actually run**; the result is recorded in `BUILD_LOG.md`.
- Security-critical paths (auth, authorization, presigning, CSV parsing) have
  tests, not just implementation.
- Do not advance past a failing gate. Fix it, or log it as a blocker per 9.7.

## 9.6 Quality bar
- Authorization is enforced server-side on every route; the frontend only hides UI.
- No plaintext passwords or tokens in logs. Validate all inputs. Use parameterized
  queries only.
- Keep backend memory low: streaming, bounded batches, no unbounded in-memory
  caches. Report measured peak memory for the 10k-row import test if it can be
  measured; otherwise state that it was not measured.
- Keep the first-load bundle small; lazy-load admin and heavy views.

## 9.7 When to stop and ask
Do not stop for routine decisions; make the call, log it in `DEVIATIONS.md` or the
Assumptions section, and continue. Stop and ask only for:
- a required input that does not exist and cannot be mocked (for example a real
  secret needed to run a test that cannot use the local stand-in),
- a conflict between two "final" decisions in section 3,
- a gate that stays failing after reasonable attempts (report what you tried),
- the configured checkpoint has been reached (see 9.9).

## 9.9 Checkpoint behavior (BUILD_SCOPE = checkpoint)

When the gate for milestone CHECKPOINT_AFTER passes, stop. Do not begin the next
milestone, even if budget remains. Before stopping:

1. **Leave the repo in a runnable state.** `docker compose up`, migrations, seed,
   lint, and the test suite must all work for the milestones completed so far.
   No half-written files or stubs for later milestones outside the documented
   interfaces.
2. **Update `docs/BUILD_PLAN.md` and `docs/BUILD_LOG.md`** with final status of the
   completed milestones and the deferred ones.
3. **Write a checkpoint report** (replaces the 9.8 final report) containing:
   - what was built and where (file map),
   - test results actually obtained (counts, anything skipped or failing),
   - anything not done or not verified,
   - assumptions and entries in `docs/DEVIATIONS.md` that need the reviewer's decision,
   - a **review checklist** for the human: how to start the stack locally, how to
     exercise the importer with a sample CSV, how to log in as the bootstrap
     Registrar, and which permission-matrix and security tests to read first,
   - the list of remaining milestones with a rough size estimate for each.
4. **End with the exact resume instruction:**
   "To continue, reply `continue from milestone N`, or change CHECKPOINT_AFTER or
   set BUILD_SCOPE to `full`."

On resume, first re-read `docs/DESIGN.md`, `docs/BUILD_PLAN.md`, `docs/BUILD_LOG.md`,
and `docs/DEVIATIONS.md`, and apply any review feedback the human gives before
starting the next milestone. Do not redesign completed milestones unless the
feedback asks for it; log any change in `DEVIATIONS.md`.
